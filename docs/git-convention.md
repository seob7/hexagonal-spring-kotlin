# Git 협업 명세서

- **목적:** 멀티모듈 모노레포 환경에서 코드의 병합 충돌을 최소화하고 유기적인 공동 개발을 진행하기 위한 규칙입니다.

---

## 1. 브랜치 전략

배포 주기가 단순하고 명확한 프로젝트 특성을 감안한 브랜치 구조입니다.

```text
  main (상용 배포 브랜치)
   ▲
   │  [Release / Merge]
   ▼
  develop (통합 개발 브랜치)
   ▲
   │  [Pull Request]
   └─────────────── feat/기능명 (개발자 작업 브랜치)
```

- **`main` 브랜치:** 상용 운영 환경에 배포되는 가장 안정적인 브랜치입니다. 직접 푸시할 수 없으며 오직 `develop` 브랜치로부터의 병합만 가능합니다.
- **`develop` 브랜치:** 로컬 개발 결과물들이 병합되는 메인 통합 브랜치입니다.
- **`feat/` 브랜치:** 개발자들이 실제 요구사항을 개발하는 개인 작업 공간입니다.
    - **네이밍 형식:** `feat/{기능명}` — *예:* `feat/reference-search`

---

## 2. 커밋 메시지 규칙

커밋 내역의 추적 가독성을 높이기 위해 시맨틱 커밋 가이드라인을 준수합니다.

### 2.1 기본 포맷
> **`타입: 작업 내용`**

- 첫 글자는 소문자로 작성하며 한글로 간결하게 작업 내용을 기술합니다.
- *예시:* `feat: 레퍼런스 삭제 유스케이스 구현`

### 2.2 허용되는 커밋 타입

| 타입명 | 설명 | 예시 |
| :--- | :--- | :--- |
| `feat` | 새로운 기능 및 API 구현 | `feat: 레퍼런스 목록 조회 API 구현` |
| `fix` | 버그 및 오류 수정 | `fix: 논리 삭제된 레퍼런스가 목록에 노출되는 문제 수정` |
| `refactor` | 코드 리팩토링 (기능적 변화 없음) | `refactor: 페이지 조회 QueryDSL 쿼리 정리` |
| `docs` | 문서 작성 및 수정 | `docs: 헥사고날 아키텍처 README 추가` |
| `test` | 테스트 코드 작성 및 수정 | `test: ReferenceService 단위 테스트 구현` |
| `style` | 코드 가독성용 포맷 변경 | `style: 구글 코드 정렬 포맷 일괄 적용` |
